> 这篇的底稿是两段加起来 80 多分钟的语音分享。依然延续这个系列的传统——**作为人类，你只需要读懂思路和逻辑；具体的执行细节，把文章丢给你的 Agent 就行。**

## 开头：两个关键词

今天聊一个稍微有点抽象的命题：如果 Agent 时代只能记住两个词，应该是哪两个？

第一个毫无疑问是 **Context**，上下文。

从模型训练用的数据，到模型应用时你给它的代码仓库、企业知识、个人习惯，本质上都是上下文。可以说，上下文在八成的层面上已经决定了输出的质量。这也是我之前那篇 [Context is All You Need](../context-is-all-you-need/) 想表达的逻辑。

第二个词，我认为是 **Loop**，循环，或者说闭环。

一件事只有迭代成闭环——有日志、有记录可以复盘，改完之后又能验证结果——Agent 才能不断提升自己的决策质量。这其实已经有点模型训练的雏形了，更进一步就是大家常说的自我进化。听上去有点高大上，但它完全可以落到我们自己的工作流里：**有意识地去构造 Context，有意识地去构造 Loop。**

这两个词之间的关系，就是这篇文章的主线：

- **静态的 Context**：预先写好的东西。规则文件、Skill、记忆、工具配置。
- **动态的 Context**：只能从 Loop 里长出来。你做了验证、拿到了结果、复盘了错误，这些新信息再回流成下一次的上下文。

一个具体的数字感受一下。我有个仓库叫 agent-config，7 月 23 日建的，两个月过去，它累积了大约 1.6 万次提交、1800 多个 issue、将近 2000 个合并的 PR。我现在每天大概消耗 20 到 30 亿 Token（含缓存读取）。之前要维持这个量级，我得高频地人在环内盯着；现在，**同样量级的 Token 消耗，单个项目明显省心得多**，我每天只花一小部分时间在 Agent 上面，不影响做其他事情。

这背后的功臣，就是 Context 和 Loop。

> 主脑调度、执行层干活、门禁把关的整体架构，我在 [将军赶路不追小兔](../260809-multi-agent-scheduling-architecture/) 里已经详细讲过；工作台比喻和上下文管理的基本方法在 [Context is All You Need](../context-is-all-you-need/) 里。这篇不重复，直接往下走。

## 一、为什么偏偏是这两个词

还是从 Coding 这个场景说起。为什么 Coding 是 Agent 最早能大规模落地的场景？本质上是三点：

1. **高价值**：写代码贵，省下来的都是钱。
2. **数据高质量且充分**：开源代码、文档、问答，训练数据管够。
3. **验证可闭环**：代码能跑、测试能过、编译器会报错。

第二点对应 Context，第三点对应 Loop。Coding 恰好两个条件都满足，所以跑得最快。

更重要的是，**这两件事和你具体用什么模型没有关系**。这两个东西搭好了，不论你用顶级模型还是便宜模型，都能帮你提高决策质量、减少 Token 浪费。模型能力的提升是别人在卷的事，你能控制的，就是上下文和循环。

Cloudflare 有篇文章开头说得很直白：

> *"AI has made the step that was previously the slowest and most expensive — implementation — the fastest and cheapest."*（AI 把过去最慢、最贵的那一步——实现——变成了最快、最便宜的。）
> —— [The Agent Development Lifecycle has arrived on Cloudflare, Cloudflare](https://blog.cloudflare.com/agent-development-lifecycle/)

写代码不再是瓶颈了。瓶颈移到了两头：前面是"你给了它什么上下文"，后面是"你怎么验证它做对了"。这正好就是 Context 和 Loop。

## 二、静态 Context：每样东西都要回答"它凭什么在这里"

先聊静态的部分，也就是我们自己能控制的那部分。

一个 Coding Agent 的上下文，不论开源闭源，大致是这么几层：

| 层次 | 例子 | 能不能改 |
|---|---|---|
| 预置 prompt | Claude Code、Codex 内置的工程习惯 | 闭源基本不能；开源的 Pi 可以自己组装 |
| 全局规则 | `~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md` | 能 |
| 项目规则 | 仓库根目录的 `CLAUDE.md` / `AGENTS.md` | 能 |
| MCP | 各类工具服务 | 能 |
| Skill | 全局和项目的技能包 | 能 |
| Memory | 跨会话的记忆 | 能 |

过去一个月，我对这几层做了非常多的审查和测试，删减增改，目标就两个：提高任务完成质量，降低 Token 消耗。

先说一个贯穿始终的原则：**像珍惜你自己的注意力一样，珍惜 Agent 的上下文窗口。** 所有出现在上下文里的东西，原则上都需要被治理，都需要问一句：它真的有必要在这里吗？没必要，就剔除。

再补一个概念：**我认为 Git 是 Agent 时代最好的软件，也是基石。** 它用很低的成本存储了每个版本的差异。你所有的行为轨迹，都可以追溯到当时用的是哪个版本的 prompt、什么样的上下文、哪个 harness（也就是 Claude Code、Codex 这类包在模型外面的那层工具壳）、什么样的代码逻辑。所以下面说的每一层，都应该进 Git 仓库，甚至同步到 GitHub，长期迭代。

### 预置 prompt：基本不用管

各家 Agent 自带的系统提示，闭源的你改不了，开源的像 Pi 你可以自己组装。但大部分情况下，用默认调好的就行。这一层我们后面在执行层还会再提到。

### 全局规则：不是一次性的，而且要分层拼接

很多人把全局的 `CLAUDE.md` 或 `AGENTS.md` 当成一次性的行为，写完就不管了。我觉得这不太好。它应该进仓库、长期迭代，**有加法，也要有减法**。

说到减法，最近有个很有代表性的事情。Claude Code 团队的 Thariq 发了一篇文章，讲新一代模型的上下文工程：

> *"We removed over 80% of Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5 with no measurable loss on our coding evaluations."*（针对 Opus 5 和 Fable 5 这类模型，我们删掉了 Claude Code 八成以上的系统提示，编码评测没有可测量的损失。）
> —— [The new rules of context engineering for Claude 5 generation models, Claude](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)

各家在新模型发布时都会有类似的建议：针对顶级模型，删掉历史 prompt 里那些补丁，别再强调"多想一点、再深一点"。

他们说得对不对？肯定是对的。毕竟是他们自己训练的模型，他们有最多的使用经验。

**但我的建议是：方向照着走，节奏晚六个月。**

原因很简单，他们的最佳实践建立在一个我们没有的前提上——几乎无限的高智力 Token。这一点三家都亲口承认过：

- Pragmatic Engineer 写 OpenAI 内部软件工厂的文章，开篇第一句：*"It's rare to work with an unlimited token budget, but at OpenAI, that's what all engineers… do."*（无上限的 Token 预算很少见，但 OpenAI 的工程师们都是这样工作的。）
- Thariq 在 [Latent Space 的访谈](https://www.latent.space/p/thariq) 里也随口说了一句 *"we have lots of tokens"*。
- [Orca 创始人的访谈](https://www.superlinear.academy/c/recording/orca) 里也提到，模型公司内部的人处在 Token 充足的环境里，很少碰到外部用户天天遇到的额度用完、要换供应商接力的摩擦。

我们这些圈外人很难这么奢侈。很容易出现的情况是：你这边按顶级模型把 prompt 删干净了，过两天额度用完，被迫换成一个普通模型——之前针对普通模型打的补丁没了，质量可想而知。只能等六个月之后，高智力 Token 的成本降到一个新的层级，再真正照做。

那怎么办？Thariq 在那期访谈里聊到一个很有意思的点。他说失败模式是随模型变化的，连 Fable 5 和 Fable 5.1 都不一样；主持人顺口接了一句"那你得有 Fable.md、Opus.md"。Thariq 的回应是：确实，但维护好几份非常痛苦，而且一直累积失败模式的记录，大概率会把模型约束过度。

我的情况更尴尬。我用的东西特别杂：Claude、Codex、Cursor、Kimi、Grok、GLM、MiniMax、Gemini、DeepSeek，还有各种免费模型。不可能每个模型维护一份规则文件。但这个需求又客观存在。

我目前的工程实践是**分层拼接**。把规则文件拆开：

1. **不随模型变的**：你的工程习惯。比如必须走 TDD、你独有的测试验证手段。这部分长期存在。
2. **随模型能力变的补丁**：给普通模型的"多想一想"之类的强调。顶级模型（GPT-6、Fable 5.1 这一档）基本不需要，拼接时就不带。
3. **随模型个性变的反约束**：比如 GPT 系模型通常极度严谨、容易过度设计，那就给它加一条反过度设计的约束。

三块按"哪个工具、哪个模型、什么角色"动态拼起来，生成它的规则文件。效果上近似"每个模型一份"，但你只维护一套源文件。同时它进版本管理，随着数据回流做回测，做加法的同时做减法。

在这个基础上，我还给注入量上了一道硬闸：主脑侧的规则每侧不能超过 24KB，提交时超了就直接拒绝。有一段时间规则源一度涨到 24.5KB，几乎贴线；后来把主脑才需要的流程内容迁到按需加载的技能里，压回到 19.8KB 左右。**有了这道闸，加一条规则之前就必须先想清楚要删哪条。**

顺带一提，现在 Claude Code 也开始兼容 `AGENTS.md` 了，你可以在 `CLAUDE.md` 里用一行 `@AGENTS.md` 引用它，全局只维护一份文件就够了。

### 项目规则与 Memory：有进口，也要有出口

项目级的规则文件已经天然在项目的版本管理里，这点还好。要想清楚的是**边界**：什么进 `AGENTS.md`，什么进 Memory。

我的划分是：**长期不变的约束**进 `AGENTS.md`；**部署习惯、犯过的错误**这类东西进 Memory。而且两边都要有入口，也要有出口——会增加，也要会删除。

这里要单独说一下 Memory。

我现在会用非常多的客户端：Claude Code、Codex、Grok、Cursor、Kimi、OpenCode、Pi。这种情况下，**你就不能依赖某一家自带的记忆系统了**。很可能 Claude 这边改完了，交给其他 Agent 去实现，那边接手之后不会更新到 Claude 的记忆里。结果 Claude 的记忆反倒成了整个系统里和现实最不符的地方。

所以我在开发机上把 Claude Code 自带的记忆关了，自己维护了一套。说起来也没什么难的，本质上和 Claude Code 的记忆逻辑一样：一个索引目录加一组 Markdown 文档，有增加、有更新、有删除。在全局规则里约束一下，所有 Agent 都会一起维护它，记忆就能在不同主脑之间流畅地协作。

有两个设计取舍值得一提：

- **不上向量库。** 我的判断是，瓶颈不在召回率，而在加载了过期的记忆。与其让它"找得更准"，不如保证它"存的都是对的"。
- **教训不进记忆。** 踩坑走另一条路——issue，后面 Loop 部分会讲。

X 上也有人得出类似的结论，[@kunchenguid](https://x.com/kunchenguid/status/2067728608584675465) 说得很干脆：

> *"as a user, it's much better to disable 'auto memory' and make claude store memory into standard locations such as AGENTS.md or AGENTS.local.md that is agent-agnostic and portable"*（作为用户，更好的做法是关掉自动记忆，让 Claude 把记忆存进 AGENTS.md 这种和具体 Agent 无关、可以迁移的标准位置。）

反过来说，如果项目比较小，**干脆就不要 Memory**，一切以代码库为准。通过优化代码结构、建立代码图谱、优化命名、限制文件行数这些工程手段，降低 Agent 理解仓库的成本。只有项目确实上了规模，Memory 才是必须的——它能帮你降低重复踩坑的概率。

### MCP：能用 CLI 就用 CLI

如果我是做 SaaS 平台的，我非常喜欢 MCP，它比较完美地解决了鉴权这类麻烦事。但站在 Agent 使用者的角度，我挺反感 MCP 的——它对上下文空间的占用还是太大了。

所以我的习惯是：**有 CLI，就优先给 Agent 用 CLI**。MCP 放到项目级别控制，非必要不开。

这个判断有人做过对比。Pi 的官方账号 [@pidotdev](https://x.com/pidotdev/status/2090763462217551976) 引用过一项研究：

> *"They found that in domains with a mature CLI ecosystem, agents without MCP baked in completed the task just as reliably and were 5-28x cheaper."*（他们发现，在 CLI 生态成熟的领域，不内置 MCP 的 Agent 完成任务同样可靠，而且便宜 5 到 28 倍。）

### Skill：只吸收，不安装；要装就装到项目里

我在之前的文章里也说过，除了 gstack 这类少数几个，我很少直接安装第三方 Skill。大部分都是尝试着把它**吸收到自己的工程体系里**；就算安装，也是装到项目级别，尽量不全局安装。

原因还是上下文。Skill 的描述虽然占的空间小，但它毕竟占在那里，就有可能对结果产生影响。和这个项目无关的 Skill，原则上就不应该出现在这个项目里。

举个例子，飞书的 CLI 带了很多 Skill。有些项目根本用不到飞书，有些项目只用到零星几个，比如多维表格、妙记，其他的全是噪音。我的做法是：全局只装每天高频用的东西，其他的通过项目级开关单独打开。

这件事上踩过一个挺典型的坑。我们都知道 Coding Agent 的大头是 Claude Code 和 Codex，其他家要么主动兼容，会去读它们的配置文件、规则文件、Skill。其中最离谱的是 Grok：它的兼容扫描会把 `~/.claude/skills` 整个吃进去，有一阵子我的 Grok 主脑常驻了 197 个 Skill。它本身是 50 万的上下文窗口，结果还没开始干活，就被这些重复的东西占掉了不少。单独治理之后，降到了 41 个。

X 上 [@theoakatheo](https://x.com/theoakatheo/status/2106427980079829232) 提到的一个例子也很直观：有人只是删掉了没用的 Skill、把流程性内容挪出 `CLAUDE.md`，**启动时的上下文就从 35k Token 降到了 13k**。

几个月前做项目级开关，Claude Code 是做得最完善的，其他家缺一点、漏一点，我只能用软链接这类比较周折的方式变相实现。好消息是，现在 Codex 和 Pi 也都原生支持项目级的 Skill 配置了，只是粒度不一样。如果你只用一家工具，直接用它自带的开关就行；如果你像我一样用很多家，那就得自己建一层统一的开关。

不管怎样，**网上看到别人分享的 Skill，最优解是吸收内化到自己的工作流里，其次是装到具体仓库，最后才是全局。**而且所有 Skill 都要进版本管理，随着模型能力增长，该删就删，该修就修。

### 会话内：别在错误的方向上纠正，回到没犯错的地方

前面说的都是开工前就能准备好的上下文。会话进行中也有一个半动态的问题。

我非常喜欢用的一个功能是**回退**：Claude Code 里的 `/rewind`，Pi 里的 `/tree`。

理解大语言模型的基本原理就知道，它是基于前文推断后文的，**前文的所有信息都会影响后文的输出质量**。如果你判断它已经走错了方向，最好的做法不是在当前对话里让它纠正，而是**回到它还没犯错的那个节点，重新出发**。这样它的"脑海里"根本就没有那些错误的方向。

你还可以在回退点顺手告诉它："XX 方向我们已经验证过了，不用再探索。"它就会直接走另一条路。对输出质量来说，这比在一堆错误信息上打补丁高效得多。

### 引入新工具：先用自己的日志回测

最后一点，关于各种"帮 Agent 省 Token"的工具。

别人推荐这类工具的时候，最应该做的不是马上装，而是**让 Agent 结合你本地的工作日志分析一下，对你的场景到底有没有必要**。决定试用之后，过一段时间再做一次回测：它到底有没有起到它宣称的作用？还是带来了副作用？

RTK 就是我先装后卸的例子。它宣称部分场景下能省 90% 的 Token。我回测了本机 1505 次调用，实际省了 44%——听起来也不错，但**其中 87% 的节省来自搜索和读文件这两类操作，而恰恰是这两类最怕被压缩**：搜索结果会静默丢行，文件内容被压缩后，Agent 编辑时对不上原文，反而要绕过工具去找原文。后来我就把它的集成拆掉了，不再使用。

**任何帮 Agent 省 Token 的工具，你都要判断它是真的在帮 Agent 更好地理解上下文，还是引入了新的复杂度。**

## 三、把 Context 治理推到执行层

上面聊的是主脑那一层。这一节聊执行层——也就是第二段录音里补充的内容。

### Flash 级模型已经过了 Coding 的基准线

先交代背景。我现在每天消耗的 Token 很杂，市面上常见的套餐基本都买了：Claude、Codex、Grok、Kimi、MiniMax、GLM。

整个 Token 的使用呈一个**先分后合**的趋势。最早只有 Claude Code 和 Codex；后来为了节省高智力 Token 的额度，又买了一堆第三方套餐，用的客户端和模型都变杂了。

但这段时间，一个月几千张执行器任务对比下来，我发现：**至少在"主脑调度、执行器执行"这个场景下，各家执行器完成任务的成功率和质量其实差不太多**。近 90 天的验收记录里，几家主流执行器的通过率都落在 88% 到 93% 之间。当然，每家接到的任务不一样，这个数字只能说明"实际跑下来都能用"，不能严格证明质量相同；表现明显不行的也会被淘汰——有一家只有 50%，已经下线了。

这呼应了我之前的一个判断：**各家 Flash 级别的模型，已经让 Coding 这件事过了一个门槛的基准线。**过了基准线之后，在执行层拆好子任务的前提下，选模型要考虑的成本、速度、质量三个维度里，质量大家都差不多了，**你只需要考虑成本和速度**。

我觉得模型的"强"有两种：

- **全方位的强**：审美、思考、执行都很强。典型的是 Anthropic 的 Fable 5 和 Opus 5.5。
- **定向的强**：通过后训练让它在 Coding 或普通办公任务上性价比特别高。典型的是 DeepSeek v4.1 Flash，还有各家的 Flash 模型。

如果你不是家里有矿，完全可以通过**分层的任务调度**来省钱：全方位强的模型做高价值的判断，具体执行交给定向强的"牛马模型"。DeepSeek v4 Flash 这类模型输出速度很快，并发很容易拉上去，某种程度上能让你体会一下"500 刀会员"的感觉。

Box 的 CEO [Aaron Levie](https://x.com/levie/status/2079402164988895293) 说过一句很准确的话：

> *"Once a frontier planner has collapsed the ambiguity into a detailed, explicit instruction, less expensive models simply have to follow it."*（一旦前沿模型把模糊性压缩成了一份详细、明确的指令，便宜的模型只需要照着做就行了。）

### 把 Pi 当成所有主脑的子代理

接下来是我最近的一个调整，可能有点反直觉。

我之前一直强调一个观点：**好的模型一定要和它自家的 harness 强耦合**。因为顶级模型训练的时候，就考虑了 harness 里有哪些工具可以调用。这个观点我现在依然不变。

但我现在把 Codex、Grok、Kimi、MiniMax、GLM 这些额度，**优先统一派到 Pi 上面去用**。

原因是我给"强耦合"加了一个限制条件：**它适用于高难度、开放式的任务**。而在主脑已经把子任务拆好、安排好的执行场景下，我做了对比，同一个模型、同样的上下文，用 Pi 和用它原生的客户端，难分伯仲。

今天刚做完一轮对比，同一家模型，Pi 对原生客户端，一共 12 对：

| 模型 | Pi 胜 | 原生胜 | 结论 |
|---|---|---|---|
| Codex | 3（其中 1 场暂计） | 1 | Pi 不比原生差 |
| Kimi | 2 | 2 | 打平 |
| Grok | 1 | 3 | Pi 稍弱 |

合计 6 比 6。输赢主要看执行器有没有守住任务卡的要求，和用 Pi 还是原生关系不大。

更早一轮是同一个 DeepSeek 模型，跑在 Claude Code 和 Pi 上做对比。一开始 Pi 落后约 0.4 分；后来发现 Pi 这边的上下文有三类问题——任务提示首轮没注入、整池 83 个 Skill 全塞进来、规则重复注入。修掉之后，**Pi 的系统提示从 3.87 万字符降到 1.67 万，首轮输入从 1.75 万 Token 降到 8500**，第三批 8 个例子里 Pi 赢了 5 个，质量持平略优，每份成本还低了约 40%。

结论很清楚：**差距主要来自 harness 给模型的上下文，而不是模型本身。**

而 Pi 的好处就在这里：**它可以完全由你自己组织上下文**。其他官方原生的 harness 当执行器时，上下文你没法定制，它可能带着一些不需要的 Skill，带着主脑那边才会用到的规则文件。用 Pi，我可以单独针对执行器这一层迭代它的上下文。既能保质保量完成任务，又能省 Token，执行器的维护成本也很低。

[@zeke](https://x.com/zeke/status/2077220539765297187) 对 Pi 有句评价我很认同：

> *"Its system prompt is small so you really feel the personality of the underlying model."*（它的系统提示很小，所以你能真切感受到底层模型本身的个性。）

简而言之：**把 Pi 当成 Claude Code 和 Codex 的子代理。** 在 Claude Code 和 Codex 里，我本质上只用最好的模型，用它们的思考智力；那些杂活，全部交给 Pi 配任意第三方模型来实现。

### Advisor：让全方位强的模型只做高价值判断

说好听点，所有这些上下文优化措施，本质上是为了提升任务执行质量、降低我的精力占用。但客观地说，它们确实也是为了省 Token，特别是省 Opus 5.5 的额度。省到最后，已经开始搞出一些"奇技淫巧"了。

其中我现在最高频使用的一个，是 **Advisor 模式**：请教顾问。

牛马模型执行任务还行，但让它做决策，大概率不太行。特别是会话进行得越长、上下文越满，它越容易陷入局部而不自知。这时候我最喜欢的方式，就是去请教 GPT-6、Opus、Fable、Kimi 这些顶尖模型。每次请教消耗不大，但得到的建议决策质量非常高，**经常直接推翻底层模型的判断**。

这个思想是从 Claude Code 学来的。它有一个实验性的原生 Advisor 工具，由主模型在关键节点去咨询另一个更强的模型。但它只能在 Claude Code 里用，而且**它会把整段对话都转给顾问**。

这一点恰恰是我后来发现最关键的地方。

我做过一个回溯盲测。找了两个已知结局的 PR——都是改了好几轮之后最终撤回的。把材料截断在第三轮修复之后、主脑准备收尾之前，不给任何能暗示结局的信息，请顾问判断"接下来怎么办"。一共问了 9 次，**9 次全部否掉了主脑当时的收尾计划**，方向和后来的实际撤回一致。

然后我逐个排除变量：

- 去掉选项菜单，改成开放提问——顾问照样提出停手。
- 把顾问的身份换成"你就是那个已经修了三轮的主脑"——它照样跳出来。
- 换一个弱一点的模型——它能说出"该停手"，但说不出"为什么这个方案本身就不该做"。

排除到最后，剩下的那个变量是：**顾问没有背着那段会话历史**。主脑修了三轮，有沉没成本，有被前文带偏的惯性；顾问没有。

所以真正起作用的，**与其说是"更强的模型"，不如说是"干净的独立上下文"**。AWS 在 SWE-bench 上做过类似的实验，结论是一句很好记的话："Hand over the repo, not the cheap model's chat."（交出仓库，别交出便宜模型的聊天记录。）X 上 [@alexfoundr](https://x.com/alexfoundr/status/2104970979512406293) 也说过：

> *"More context can make an agent worse. I gave one the whole project history and got an answer that sounded informed because it carried old decisions into a new question."*（更多的上下文可能让 Agent 更差。我给它整个项目历史，得到的回答听起来很懂行，只是因为它把旧决策带进了新问题。）

基于这个结论，我把 Advisor 写成了一个独立的工具，以类似 Skill 的形式让所有 Agent 都能用：

- 顾问跑在**只读沙箱**里，可以看代码，但不能改任何东西。
- **不带会话历史**。主脑要写一张三栏的请教卡：机械事实、我的判断、**我希望听到的答案**。第三栏是专门给顾问去反驳的。
- 什么时候请教，不靠模型自己判断（模型对自己的把握程度基本没有校准），而是靠机械信号：同一张卡修复轮次用完、门禁连续两轮报出新问题、定时审计升级过的任务卡，以及主脑在定方向前主动发起。

用下来的体感非常好。我抽样看了 21 次决策类的请教：**10 次直接反对，11 次部分同意但改掉了关键前提，完全同意的一次都没有。**

讲三个具体的故事。

**故事一：修了三轮的方案，直接放弃。** 一个合并门禁的判定逻辑，执行器已经修了三轮还不收敛，主脑正在两个降级方案之间挑一个，准备进第四轮。顾问的回答是：这张卡本身就不是红线的防线，它只会让红线变弱，两个降级方案都不要，这一版直接放弃。它还指出，三轮的问题都落在同一块，原因是这张卡选了唯一一条必须靠猜的路。最后这个 PR 关了，没合并。

**故事二：补丁越补越多，唯一安全的是"一条都不留"。** 一个拦截危险命令的安全钩子，里面有一组"先切换目录再删除"的豁免规则，已经补了好几轮，主脑还想继续收紧。顾问先做了个只读实验，证明切换目录这个命令本身可以被同名函数改写，然后给出结论：只看这些命令文本，不存在能证明安全的非空豁免集合，唯一可证明安全的是空集。主脑采纳，把这组豁免全删了。

**故事三：排在最后的，其实应该排第一。** 给一个付费的服务排接下来几个小时的待办，主脑把一个"尚未定性"的告警问题排在了最后。顾问说：你的排序有两处错，这个问题应该排第一——它是唯一一类已经实际伤害过真实付费客户的缺陷：用户付了款，卡在某个状态 62 天，没人知道。当晚这个问题就修掉了。

当然，顾问也会错。有一次它关于"原有路径已经会报错"的推断，就被真实的复现推翻了。所以顾问的意见同样要验证——这一点，下一部分会展开。

**全方位能力强的模型，用来做高价值的判断；具体的底层执行，交给牛马模型。** 这就是我在执行层的 Context 治理思路。

## 四、Loop 的标本：一个两个月的配置仓库

静态的 Context 基本说完了。接下来聊动态的 Context，也就是第二个关键词：Loop。

### 它是怎么长成这样的

agent-config 这个仓库，最初只是为了管理上面说的那些上下文——同步规则文件、管理 Skill。后来慢慢加入了主脑调度执行器的体系，加入了终端角标的状态监测，再后来，它演变成了我所有 AI 学习的基础仓库。

它的演化路径大致是：

1. 配置同步仓：一份公共规则，各工具一层薄薄的专属段。
2. 多执行器路由：按额度和任务类型自动选执行器。
3. 主脑调度：派卡、等待、验收、记分。
4. 意见箱：跨仓的教训统一汇报回来。
5. 规则瘦身与注入预算闸。
6. 自建 Memory。
7. 请教顾问。

每一步都不是预先设计的，而是在使用中长出来的。

它最重要的一点是：**它已经有了一个 Loop 的雏形**。这个仓库相当于我整个 Agent 调度体系的根。我要求所有在用这套体系开发其他仓库的会话，遇到调度层面、脚本层面的问题，都在收工的时候统一汇报到 agent-config 的 issue 里。然后我每天再专门派 Agent 去处理这些 issue。

因为我每天都有很高强度的开发，所以这个仓库汇集了非常多的反馈。两个月下来，1800 多个 issue，其中专门记录教训的就有 1100 多张；将近 2000 个合并的 PR。

### 飞机引擎边飞边换

说实话，这个过程非常辛苦。

这个仓库既是整架飞机的引擎，又是我们要修理、要更换的东西。前期就是一团乱麻，冲突特别多。经过一段时间之后，它才慢慢平稳下来、收敛下来。很多问题在过程中得到了解决；新增的问题，要么能和之前的问题关联上，要么新增的频率降下来了。

从数据上看，每周新开的 issue 在 9 月第一周达到峰值 305 张，到 9 月最后一周回落到 159 张。

关一张教训单的标准，我只问一句：**这个坑，现在还踩得到吗？** 踩不到了，才能关。不是"修了"就关，而是"机制上不可能再发生"才关。

### 同一个错，不犯第二次

讲几个具体的坑，感受一下"吃一堑长一智"在工程上是什么样子：

- **测试打到了生产。** 执行器开新的工作区时，只链接了仓库根目录的 `.env`，深层目录的配置文件缺失，代码就静默地回落到了默认配置——连上了生产环境。后来，建工作区这件事被做成了一个脚本，自动逐层链接所有配置文件，人和 Agent 都不再手工建。
- **推送成功了，又被推了两次。** 为了让输出短一点，Agent 习惯在 git 命令后面接 `| tail`。结果管道吞掉了推送失败的退出码；另一次反过来，`head` 截断了输出，让一次成功的推送看起来像失败，被重推了两轮。后来定下规则：判断"推上去没有"，一律去查远端，不看本地。
- **执行器把活又派给了自己。** 一张任务卡忘了写执行器的角色声明，执行器读到了主脑才该看的派发规则，把任务又派了出去，空转了 90 分钟，零产出。后来任务卡模板强制带角色声明，执行器拿到的规则里直接剥掉主脑段。
- **查一个布尔值，花了几万 Token。** 主脑想确认一个服务是否在运行，用了一条会把整张任务卡内容打印出来的命令，几万 Token 就这么灌进了上下文。这是 Context 和 Loop 交汇的例子：上下文的浪费，也要靠复盘才能发现。

### 写进提示，不如写进代码

教训沉淀到哪里，也有讲究。Anthropic 的 [AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) 里有一条很实用的规则：

> *"When Claude makes a mistake twice, the correction goes into CLAUDE.md."*（Claude 同一个错犯两次，就把纠正写进 CLAUDE.md。）

但同一篇文章紧接着也说了，Skill 只能让违规变少，Hook（确定性的脚本）才能让违规几乎不可能。

xAI 的 Lauren 在一个分享里把这件事讲得更彻底。她把约束分成几层，从强到弱：**代码结构和架构**（让错误在结构上不可能发生）> 静态分析和 lint > 规则和 Skill > 只能靠人审的风格指南。每纠正一次 Agent，就从强到弱，找到最有效的那一层沉淀下来。

X 上 [@kabelsalat_info](https://x.com/kabelsalat_info/status/2106456492719415400) 说得更直白：

> *"A failing check gets fixed every single time, a line in AGENTS.md gets ignored on a bad day."*（一个失败的检查每次都会被修，而 AGENTS.md 里的一行字，赶上状态不好的时候就会被忽略。）

上面那几个坑，最后能真正根治的，都是变成了脚本、闸门和测试的那些；只写进规则文件的，过一阵子还会以别的形式冒出来。

### 一个诚实的反证

我也得说一个不太好看的数据。

按周统计验收通过率，8 月中旬一周是 97%，到最近一周降到了 80% 左右。原因我还没有完全确证：可能是便宜的执行器进了执行池，可能是验收变严了，也可能是后来新加的"升级"这类结果项改变了统计口径。

我把它写出来，是因为这本身就是 Loop 的一部分：**体系在变，指标本身也要被审视**。一个只会变好看的指标，大概率是哪里坏了。

## 五、低成本的验证通道，以及"验证也要被验证"

Loop 能不能转起来，关键在于你有没有**低成本、高效率的验证方式**。这是我现在最关注的领域之一。

### 验证通道的光谱

从便宜到贵，大致是这样的：

1. **编程语言本身**。我最近明显的一个变化是，不太关心底层用什么语言了。站在今天这个时间点，我认为写代码这件事已经是一个被解决的问题，但软件工程——对复杂度的管理——是长期存在的。选语言，过去看"我擅不擅长"，现在看"**这门语言对 Agent 友不友好**"。Rust 就很友好，很多错误编译根本过不去，Agent 马上就能修掉；其次是 Go，再往上是 Python。另一个坐标是业务需要：简单脚手架用 Python，高性能用 Go 和 Rust。
2. **测试**。后端可以用测试把行为锁死。
3. **前端录屏**。让 Agent 录屏，再去 review 视频。
4. **代码审查**。比如阿里出品的 OpenCode Review，能以比较低的 Token 成本审查代码；还有我们自定义的 Agent 审查。
5. **门禁**。把以上这些串起来，全绿才能合并。

这些验证通道会把反馈回传给 Agent，它马上就能知道自己写的代码有没有问题、错在哪里。生产环境遇到 bug，修掉之后也要回溯：当时为什么犯？下次怎么规避？这也构成一个 Loop。

### 代码廉价，测试昂贵

在 Agent Coding 的时代，**代码是很廉价的，测试是非常高价值的**。

有没有一个清晰明确、能形成反馈的验收标准，已经成了现代软件工程的核心目标。如果你的目标能拆解成一系列可以验收的条件，那对所有 Coding Agent 而言，剩下的一切都只是时间问题、成本问题，迭代就好了。

像重写数据库、迁移代码仓库这类事，只要测试是完备的、踩过的坑都以测试的形式内化了，我觉得完全没有什么难度，只是单纯地堆成本：上最好的 Token，上最好的 harness，Coding Agent 就能完成。

最麻烦的是那种**你不知道怎么拆成可量化反馈**的目标。比如前端审美，就很难量化，也就很难形成 Loop，很难持续迭代优化。

### 判据也会失效

这里有一个很容易被忽略的问题：**你用来验证的东西，本身也需要被验证。**

我的门禁系统 gate-hub 是我 Token 消耗第二大的仓库，在它身上，这类坑踩了不少：

- **草稿期的假绿。** PR 处于草稿状态时，模型主审整个被跳过，汇总结果把"跳过"当成"通过"，照样显示绿色。等标成正式之后，连红三轮。
- **钉住了版本，没钉住行为。** 引用的工作流明明钉在一个固定的提交上，但它内部又引用了主干的最新版。主干一更新，八个仓库同时挂掉，而草稿期的假绿又把这件事掩盖了。
- **机器空着，任务在排队。** 换了版本之后，运行器的白名单没同步，任务永远派不出去，也没有任何告警。三次分别排了 40 分钟、2 个多小时、8 个多小时，而运行器明明在线、空闲。
- **没人读的名单。** 代码审查被挪到"仅建议"名单后，没有任何流程去读这个名单，32 个仓库静默地停掉了审查，退出码全是正常。
- **从没判过卷的金丝雀。** 我设计了一套"合成考卷"，用已知有问题的代码定期考审查模型，检测它有没有"活着但变笨了"。结果跑了一个多月、111 次，因为凭据一直没配好，一次卷都没判过。

这些坑有一个共同点：**它们都是绿的，都没报错。**

所以我现在有一条硬规矩：**任何判据写完之后，先喂一个已知答案为"否"的输入，确认它会变红。** 一个永远不会变红的检查，等于没写。

### 闻过则喜

所以要非常珍惜开发过程中犯的那些错误。派另一个 Agent 去读工作日志，判断它为什么犯这个错误；该积累的积累下来，日后统一做第一性原理的处理。

客观上，这也是一种闻过则喜。

## 六、瓶颈转移：从人到算力

当你把这套体系搭起来之后，会发现一件事：**你的精力突然不是瓶颈了，瓶颈变成了硬件。**

### CI 成了新的堵点

OpenAI 那篇软件工厂的文章里，基础设施负责人 Venkat Venkataramani 说：

> *"We're talking about roughly a 10x increase in load on some systems. At most companies, that kind of growth might happen over two or three years. At OpenAI, we see it in about six months."*（部分系统的负载大约涨了 10 倍。大多数公司要两三年才会涨到这个量，OpenAI 大约半年。）
> —— [Inside OpenAI's agentic software factory, The Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/openai-software-factory)

这一点我深有感触。我现在经常同时调度 20 个主脑，下面三五十个执行器在跑。并发上去之后，开发机的 CPU、CI 流水线的 CPU，都成了卡点。之前那台 12 核的开发机，经常连续几个小时 CPU 打满。

门禁这边的变化更明显。CI 的运行器槽位，从最早的 6 个，一路扩到现在的 84 个，分布在四台机器上。有意思的是，**瓶颈的位置也在移动**：一开始以为审查是瓶颈，但审查任务主要是在等模型 API 返回，几乎不吃 CPU；真正吃 CPU 的是测试。有一次统计，审查池 35 个槽只有 3 个在忙，测试池 9 个槽忙了 5 个，第三个并发任务排了将近 9 分钟的队。

[@marcosnils](https://x.com/marcosnils/status/2104307761114751448) 有句话说得很准：

> *"Agents flood CI; throwing bigger boxes at it doesn't scale."*（Agent 会淹没 CI，单纯换更大的机器扛不住。）

但不管怎样，这些都是低成本的反馈链路，是必须建的。遇山开路，遇水架桥，解决就是了。

顺便提一嘴：**要升级硬件的话，可以早点。** 内存和硬盘的涨价已经很明显了，按当前 Agent 的发展势头，CPU 涨价恐怕也是板上钉钉的事。不论个人还是团队，如果长期有需要，都可以尽快锁定算力资源。

### Linux 还是 Mac

从 Loop 的角度，还能聊一个话题：Agent 最适合什么操作系统。

**从 Computer Use 的角度，Mac 毫无疑问是最佳选择。** 它上面的软件是给人用的，兼容性广；系统又是 Unix，API 比较完善，Agent 可以通过 Computer Use 去操作。

**但如果单纯从 Agent 自己使用的角度，最佳的操作系统一定是 Linux。** 所有东西都可以通过配置文件修改，不需要人类二次授权。Mac 毕竟有些权限需要你在屏幕上点来点去，Agent 自己没法操作；Linux 完全通过命令行，什么都能改、什么都能操作。某种意义上，Linux 给 Agent 的"root"比 Mac 更彻底。

所以如果你是纯 Coding 场景，又不依赖单一平台（比如 iOS 开发只能在 Mac 上），Linux 会比 Mac 更适合 Agent。这也是我目前的工程实践。当然，浏览器验证、Computer Use 这些能力就需要额外去补齐。

X 上也有人有类似的体感，[Theo](https://x.com/theo/status/2090528543746965991) 说换到 Linux 之后，他的 Agent 性能有了数量级的提升，尤其是文件系统那一块。

## 七、从 Coding 到组织，再到学习本身

### 名字不同，干的是同一层的事

最近冒出来很多新名词：Orca 叫 ADE（Agent Development Environment），Cloudflare 叫 ADLC（Agent Development Lifecycle），也有人叫 harness of harness。

我的理解是，它们都在同一个层级上工作：**怎样给 Agent 一个完善的工作环境，让它们协作处理复杂问题。** 至于下层单点的问题——某个模型会不会写某个函数——老老实实享受模型能力的提升就可以了。

这篇文章说了这么多，核心其实也就是这件事：为 Agent 打造一个工作环境。Context 是这个环境里的"材料"，Loop 是这个环境的"进化机制"。

### 不止于 Coding

我之所以说这是整个 Agent 时代最重要的两个词，是因为它不局限于 Coding。**Agent 想要进入的任何环境，本质上都要看这两点：有没有充分的 Context，能不能形成 Loop。**

我之前在 [老树开新花](../260908-smb-agent-framework/) 里聊过 AI Native 组织的三个层次：组织对 AI 是否**可读**，是否**可写**，是否**可闭环**。放到 Coding 里看，一个代码仓库就是一个简易版的小组织。

### 学习本身也是一个 Loop

最后说说学新东西。

以前很多特别先进的工程实践，不太可能马上落地到自己的工作流里，因为大厂的一线实践依赖非常强的基础设施。但现在，借助 Agent，个人的工程能力几乎是无限强的。

所以我现在判断一个新东西值不值得学，思路是：**把文章丢给 Agent，让它结合我本地的开发日志、过程中犯过的错、历史 issue，再结合我一个人负责的场景，判断哪些值得吸收、哪些不用管。** 别人今天分享了一个最佳实践，几个小时之后，它的核心思想可能就已经进了我的生产线。

前面说的 RTK 先装后卸、Advisor 从 Claude Code 学来又改造，都是这么来的。

## 写在最后

我会觉得，在这个时代，**如果你做一个项目越做越累，那说明你调度 Agent 的能力一定是有问题的。**

正常来说，至少在工程上，你应该越做越轻松。你的注意力会不断从项目里被解放出来，只需要关心工程之外的东西，比如流量、比如资源分配。

做到这一点，靠的就是这两个词：

- **Context**：有意识地准备上下文，每样东西都要回答"它凭什么在这里"，有加法也有减法。
- **Loop**：有意识地构建闭环，让每一次犯错都被记下来、被验证、被写进下一次的上下文。

前期可能会磕磕绊绊，但随着 Loop 转起来，你基本上不会让同一个错误犯第二次，只会遇到新的、没想到的问题——没关系，有充分的日志可以排查，再积累就好了。**Loop 构建的链路越不需要人类，它迭代得越快，你调度 Agent 的能力也成长得越快。**

吃一堑，长一智。前提是，这一堑被记下来了。

以上，一家之言，不一定对。希望对各位有所帮助。
