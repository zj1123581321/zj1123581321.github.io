# 验收记分卡

主脑在验收定局时，往业务仓的 `retro/acceptance-log.jsonl` 追加一行 JSON。
目的：把"哪个执行器做哪类任务做得怎么样"的体感变成可查询、有日期、有例子的记录，
为后续调整路由表提供证据。

## 一行记录长这样

```json
{
  "ts": "2026-07-31T14:30:00+08:00",
  "task_id": "myproject-20260730-01",
  "repo": "myproject",
  "executor": "codex",
  "model": "gpt-5.6-luna",
  "task_type": "backend-logic",
  "complexity": "M",
  "rounds": 2,
  "wall_clock_min": 53,
  "diff_lines": 480,
  "outcome": "accepted",
  "scope_discipline": 1,
  "taste": 3,
  "note": "功能正确但引入了不需要的抽象层，砍掉一半"
}
```

## 字段说明

### 客观字段（脚本自动回填）

| 字段 | 说明 |
|------|------|
| `ts` | 验收时间 |
| `task_id` | 任务卡唯一编号 |
| `repo` | 仓库名 |
| `executor` | 执行器（codex / kimi / grok） |
| `model` | 使用的模型 |
| `task_type` | 任务类型（7 种固定词表） |
| `complexity` | S / M / L |
| `rounds` | 修复轮次 |
| `wall_clock_min` | 挂钟耗时（分钟） |
| `diff_lines` | 改动行数 |

### 定局字段

| 值 | 含义 |
|----|------|
| `accepted` | 验收通过 |
| `escalated` | 升级换执行器（对原执行器是负信号） |
| `abandoned` | 放弃任务本身（不算执行器的账） |

### 主观字段（人打分，0-3）

**scope_discipline**（边界纪律，过度设计的反面）：
- 3 = 严格守住任务卡边界，无多余抽象
- 2 = 轻微越界或小冗余，不用返工
- 1 = 明显过度设计/越界，需要砍
- 0 = 大面积自作主张，返工量接近重做

**taste**（工程品味/审美）：
- 3 = 拿来即用还想抄
- 2 = 合格无惊喜
- 1 = 能跑但丑，将来要重整
- 0 = 看着就想重写

**note**（必须带证据指针）：
commit hash、文件路径或报告路径——空泛评分不可复核。

## 使用方式

1. 每次验收定局时追加一行
2. 月度复盘时按"执行器 x 任务类型"聚合，形成执行器画像
3. 画像作为调整路由表的证据依据

## 设计要点

- **词表冻结**：任务类型的 7 个词一旦定了不轻改——改了历史数据就没法对比
- **note 必须带证据**：没有证据的评分无法复核，等于没记
- **记分卡不进业务 PR**：验收定局后单独提交直推主分支，避免污染业务代码审查
