# 验收记分卡：积累对模型能力的判断力

## 解决什么问题

你用了多个模型和工具来做不同类型的任务。时间一长，你会有一些体感——"Codex 做后端稳、Kimi 做前端漂亮、Grok 快但粗糙"。但体感是会骗人的：你可能只记住了某个模型一次特别好或特别差的表现，忽略了它大多数时候的正常水平。

验收记分卡的作用是：**把体感变成数据。** 每次验收时花 30 秒打个分、记个备注，积累下来就是一份"哪个模型适合干什么活"的决策参考。

## 核心原则

1. **每次验收都记，不挑着记**：只记好的或只记差的，都会导致偏见。好的坏的都记，才能看到真实全貌。
2. **打分必须带理由**：光打分没有用——"给 1 分"不如"给 1 分，因为它加了一个没人要的抽象层（见 commit abc123）"。
3. **词表一旦定了不轻改**：任务类型的分类标准如果经常变，历史数据就没法对比了。

## 每次验收记什么

验收定局时，记下这些信息（很多可以自动填充）：

```json
{
  "ts": "2026-07-31T14:30:00+08:00",
  "task_id": "myproject-20260730-01",
  "executor": "codex",
  "model": "gpt-5.6-luna",
  "task_type": "backend-logic",
  "complexity": "M",
  "rounds": 2,
  "wall_clock_min": 53,
  "outcome": "accepted",
  "scope_discipline": 1,
  "taste": 3,
  "note": "功能正确但引入了不需要的抽象层，砍掉一半"
}
```

### 需要你打的分（0-3 分）

**边界纪律**（scope_discipline）——它有没有老老实实只做你让它做的事？
- 3 = 严格守住边界，没有多余的东西
- 2 = 轻微越界，不用返工
- 1 = 明显过度设计，需要砍
- 0 = 大面积自作主张，几乎要重做

**工程品味**（taste）——它做出来的东西你满不满意？
- 3 = 拿来即用，质量超出预期
- 2 = 合格，无惊喜
- 1 = 能跑但丑，将来要重整
- 0 = 看着就想重写

### 验收结果（outcome）

- `accepted` = 通过
- `escalated` = 质量不行，升级给更强的执行器重做
- `abandoned` = 这个任务本身不做了（不算执行器的错）

## 怎么用积累的数据

每个月拿出来按"执行器 × 任务类型"做一次交叉分析：

- Codex 做 backend-logic 平均得分多少？做 frontend-ui 呢？
- Grok 的 scope_discipline 普遍怎么样？是不是容易越界？
- 哪个执行器的 escalated 比例最高？

这些分析结果就是你调整路由配置的证据——不再靠"我感觉 Codex 好像不太行"这种印象来决策。

## 根据你的情况调整

- **刚开始用**：只记 outcome + 一句话 note 就行，打分可以后面再加。关键是养成"每次都记"的习惯。
- **只有一个执行器**：同样有价值——可以看不同任务类型的表现差异，帮你决定什么活适合交给 Agent、什么活自己做更快。
- **想自动化**：让 Agent 帮你写一个脚本，在每次验收时自动弹出表单，填完追加到 JSONL 文件里。
