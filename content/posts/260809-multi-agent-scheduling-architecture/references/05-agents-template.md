# 仓库级 AGENTS.md：给每个项目一份"团队须知"

## 解决什么问题

当你有多个项目、多个 Agent 在帮你干活时，每个项目都有自己的约定：用什么框架、怎么跑测试、命名有什么讲究、哪些文件不能碰。如果这些约定只存在你脑子里，每次 Agent 开工你都得重新交代一遍。

AGENTS.md 就是每个项目的"团队须知"——Agent 进入项目前先读这个文件，就知道该遵守什么规矩。

## 核心原则

1. **是索引不是手册**：控制在 200 行以内。详细文档链接过去就行，不要全塞进来。
2. **只写稳定的约定**：当前在改什么 bug、谁在跑什么任务——这些每天都变的东西不属于这里，属于任务卡。
3. **命令必须真实**：构建/测试命令必须从项目的实际配置文件里核实，不能编造——写错的命令比不写更害人。
4. **命名约定是给 Agent 的导航地图**：Agent 靠关键词搜索来找代码。命名混乱、同一概念多种拼法，会让 Agent 的检索效率大幅下降。

## 模板

```markdown
# Repository Guidelines

## 项目声明
- **风险等级**：personal / internal / saas
  （决定代码审查的严格程度——个人工具宽松一些，对外服务严格一些）

## 项目结构
<!-- 一句话：顶层目录是什么、代码/测试/资源在哪 -->

## 构建、测试和开发命令
```bash
npm run build    # 构建
npm test         # 测试
npm run lint     # 代码检查
npm run dev      # 本地开发
```

## 代码风格与命名约定
<!-- 写清楚以下几点，Agent 检索代码时会感谢你：
     1. 导出的函数/变量怎么命名（2-4 词，含领域词）
     2. 文件怎么命名（带领域前缀，禁止裸 utils/types/config）
     3. 同一概念用哪种拼法统一（orgId 还是 organizationId，选一个）
     4. 日志和错误消息用完整字面量，别用模板拼接 -->

## 测试规范
<!-- 测试框架、文件位置、覆盖率要求 -->

## 提交与 PR 规范
<!-- commit 格式、合并前必须通过的检查 -->

## 安全与配置
<!-- 密钥怎么管、哪些文件不能提交 -->
```

## 根据你的情况调整

- **个人小项目**：只写"构建测试命令 + 命名约定"两段就够了，其他的等项目长大了再加。
- **多人协作项目**：加上 PR 规范和安全配置段落，确保所有人（包括 Agent）遵守同一套规矩。
- **有多个相似项目**：把通用约定抽成一份共享文件，各项目的 AGENTS.md 只写自己的特殊部分。

## 一个常见的教训

很多人写了 AGENTS.md 以后觉得万事大吉，但过了几个月发现里面的测试命令已经过时了、项目结构已经变了——**过时的文档比没有文档更危险**，因为 Agent 会信以为真。所以：要么设一个定期更新的提醒，要么让 Agent 在每次开工前先核实一遍文档里的命令是否还能跑通。
