# Claude Code：让一个 Agent 内部分工

## 解决什么问题

你和 Claude Code 对话时，它既要想方案、又要写代码、又要审查——所有事情挤在同一个上下文窗口里。随着对话变长，它的注意力被稀释，容易跑偏或忘记早期的约束。

解法：让主对话只负责思考和指挥，具体干活的交给独立的"子代理"——它们在自己的上下文窗口里工作，干完把结果交回来，不会污染主对话的工作台面。

## 核心原则

1. **分工靠角色**：至少分两个角色——"执行者"负责写代码，"审查者"负责挑毛病。写和审不能是同一个。
2. **边界靠契约**：每次委派必须说清楚"做什么、能改哪些文件、怎么验证、出了问题回滚到哪"。缺任何一项，子代理应该停下来问，不要猜。
3. **主脑不动手**：主对话只做规划、拆任务、审查结果。除了单行小改，不直接写代码——这样它的上下文窗口能保持干净，专注在高价值的决策上。

## 最小起步方案

### 第一步：创建子代理角色文件

在你的项目里创建两个文件：

**`.claude/agents/implementer.md`**（执行者）：
```markdown
---
description: "执行边界明确的实现任务。任务必须包含：目标、允许修改的文件范围、验证命令、回滚点。"
---
执行边界明确的实现任务。

输入契约：任务必须给出目标、允许修改的文件范围、验证命令、回滚点。缺任何一项先停下来问。

行为准则：只改允许范围内的文件；改完必须跑验证命令；偏离计划当场记录；小步提交。

输出：改了什么（文件清单）→ 验证结果 → 偏离记录 → 残余风险。
```

**`.claude/agents/reviewer.md`**（审查者）：
```markdown
---
description: "只读审查代码改动，发现问题输出修复任务清单，绝不直接改代码。"
---
只读审查，不改代码。

审查重点（按严重度排序）：需求不符 → 逻辑错误 → 安全问题 → 缺失测试 → 命名可检索性。

输出：每个问题给出位置 + 失败场景 + 修复建议。结论：可合并 / 需修复。
```

### 第二步：在 CLAUDE.md 中加主脑规则

在项目根目录的 `CLAUDE.md`（或全局 `~/.claude/CLAUDE.md`）中加入：

```markdown
# 任务路由
主脑只做：调研、规划、拆任务、审查验收。不直接写代码（单行小改除外）。
所有实现委派给 implementer，审查委派给 reviewer。
委派时必须说清楚：目标、允许修改的文件范围、验证命令、回滚点。
```

### 第三步：开始使用

正常和 Claude Code 对话即可。当你给它一个实现任务时，它会自动把具体工作委派给 implementer 子代理，自己只负责审查结果。

## 根据你的情况调整

- **项目很小 / 任务很简单**：可以只用 implementer，不用 reviewer——审查由主脑自己做就行。
- **前端项目**：可以在 implementer 的行为准则里加上"改完必须启动应用并录屏验证"。
- **团队项目**：可以加更多角色，比如 `explorer`（只读检索，不写文件，专门负责翻代码找信息）。
- **对命名有特殊要求**：在 implementer 的行为准则里写清楚你的命名约定。

## 常见问题

**Q: 子代理会不会越界改不该改的文件？**
A: 如果你在委派时写清了"允许修改的文件范围"，它会遵守。但这不是技术上的硬限制，而是提示词约束——关键的保底措施应该放在 CI 门禁里。

**Q: 子代理跑完以后，主脑怎么知道结果？**
A: 子代理的输出会自动返回到主对话中。主脑看到结果后决定是通过、还是拆新任务让它改。
