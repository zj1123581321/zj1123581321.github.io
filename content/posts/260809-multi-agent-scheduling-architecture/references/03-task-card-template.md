# 任务卡：让 Agent 知道"做什么"和"不做什么"

## 解决什么问题

你让 Agent 去做一个任务，最常见的失败模式不是"它做不了"，而是"它做了你没让它做的事"——改了不该改的文件、加了不需要的功能、偏离了原始目标。

任务卡的作用就是给 Agent 一份"施工许可证"：**明确目标、划定边界、约定验收标准。** 有了这个，Agent 越界时你能追责，完成时你能验收。

## 核心原则

1. **没有"非目标"的任务卡是不完整的**：光说"做什么"不够，必须同时说清"不做什么"——这是防止 Agent 过度设计最有效的手段。
2. **完成条件必须是可执行的命令**：不能写"代码质量好"这种主观描述，要写"`npm test` 全部通过"这种你（或另一个 Agent）能跑的命令。
3. **修改边界是硬约束**：明确列出可以改的文件和不能碰的文件。这不是建议，是规矩。

## 模板

```markdown
# 任务卡：<一句话标题，如"给用户列表页加分页功能">

## 目标
<!-- 一两句话：做完以后用户/系统会有什么变化 -->

## 非目标
<!-- 列出容易被误以为要做、但这次不做的事。例如：
     - 不改后端 API，只改前端
     - 不做搜索功能，只做分页
     - 不重构现有组件 -->

## 修改边界
- **允许**：src/pages/UserList.tsx, src/components/Pagination.tsx（新建）
- **禁止**：src/api/（后端 API 不动）, src/auth/（认证模块不动）

## 完成条件
- [ ] 用户列表页支持分页，每页 20 条
- [ ] 分页组件支持上一页/下一页/跳转
- [ ] 所有现有测试通过：`npm test`
- [ ] 新增分页组件的单元测试

## 基线信息
- **起点**：当前主分支最新版本
- **分支**：feature/user-list-pagination
- **执行器**：（根据你的调度策略填写）
- **任务类型**：frontend-ui
- **复杂度**：S
```

## 根据你的情况调整

- **个人小项目**：可以简化，只保留"目标 + 非目标 + 完成条件"三个字段就够用。
- **多人/多 Agent 并行**：加上"唯一写入者"字段——同一时刻只有一个 Agent 能改这份代码，防止互相覆盖。
- **需要代码隔离**：加上"Worktree"字段——标记是否需要复制一份项目副本让 Agent 在副本上干活。
- **需要追踪复盘**：加上"Task-Id"字段——一个唯一编号，让每次代码提交都能追溯回这张任务卡。

## 常见问题

**Q: 任务卡写得太详细会不会浪费时间？**
A: 取决于任务的复杂度。简单任务（改个颜色、修个 typo）不需要任务卡。但只要涉及多个文件或需要几个小时的任务，写任务卡的时间远低于 Agent 跑偏后返工的时间。

**Q: Agent 真的会遵守"修改边界"吗？**
A: 提示词层面会遵守，但不是技术上的硬限制。所以关键的保底措施应该放在自动门禁里——Agent 碰了不该碰的文件，门禁直接打回。
