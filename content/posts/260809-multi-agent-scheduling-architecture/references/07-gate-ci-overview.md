# 门禁系统（Gate CI）概述

门禁系统是所有代码提交上线前的最后一道关卡。
不管是人写的还是 Agent 写的，不管是日常开发还是自动修复，走的都是同一套门禁流程。

## 核心概念

### Tier（风险等级）

每个仓库声明自己的风险等级，决定门禁的严格程度：

| 等级 | 适用场景 | 评审轮次上限 | 阻断红线 |
|------|---------|-------------|---------|
| personal | 自用工具 | 3 轮 | 数据丢失、静默出错、崩溃 |
| internal | 内网服务（≤10人） | 5 轮 | 上一档 + 越权访问 |
| saas | 对外服务 | 8 轮 | 上一档 + 注入/认证/PII泄露 |

### 审查角色

门禁系统中有三种审查角色：

| 角色 | 是否影响门禁结果 | 用途 |
|------|----------------|------|
| **chain**（主审） | 是 | 参与门禁判定，主审不通过则门禁红灯 |
| **advisory**（顾问） | 否，但结果可见 | 在关键路径上产出意见，供人参考 |
| **shadow**（影子） | 否，且不可见 | 合并后/校准采集，用于评估审查质量 |

### 门禁检查项

一次完整的门禁包含以下检查（可按仓库配置启用/禁用）：

```
1. 代码格式检查（lint）
2. 代码重复率检查
3. 依赖关系检查
4. 自动化测试
5. 改动量检查（控制在上下文窗口内）
6. AI 代码审查（主审 + 影子审查交叉）
7. 端到端测试 + 录屏（前端项目）
```

## 系统架构

```
仓库 A ──> caller workflow ──> gate（公共 reusable workflow）
仓库 B ──> caller workflow ──┘
仓库 C ──> caller workflow ──┘

gate 内部：
  review-primary  ← 主审链（决定门禁结果）
  review-shadow   ← 影子审查（不影响门禁，收集校准数据）
  review-summary  ← 汇总校准结果
```

- 各仓库通过 caller workflow 接入统一的 gate
- gate 按仓库的 tier 和配置执行对应的检查
- 新仓库接入只需在 registry 登记 + 添加 caller workflow

## 仓库接入（简要步骤）

1. 在门禁系统的 `registry.yaml` 中登记仓库信息（tier、检查项配置）
2. 在业务仓库添加 caller workflow（调用公共 gate）
3. 配置 runner（self-hosted 才能访问 AI review 所需的认证环境）
4. 首次运行 → 修复门禁发现的问题 → 进入常态

## 设计要点

1. **写代码的和审查代码的必须分开**：门禁系统的 AI 审查者和写代码的 Agent 使用不同的模型和上下文，避免"自己审自己"的自我确认偏差。

2. **门禁不全绿，别想合并**：没有例外，不因为是自动修复或紧急情况就跳过。

3. **统一复用**：所有仓库走同一套门禁模板，新仓库自动继承全套检查能力，不用逐个配置。

4. **审计留痕**：每次门禁运行都会产生审计记录（JSON artifact），包含审查结论、模型 ID、耗时等，可用于后续的审查质量评估。
