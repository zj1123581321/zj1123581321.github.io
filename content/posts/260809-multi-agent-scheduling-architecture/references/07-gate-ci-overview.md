# 自动门禁：让机器替你把关代码质量

## 解决什么问题

当 Agent 越来越多地接管代码编写，一个新问题出现了：**谁来保证 Agent 写的代码是靠谱的？**

靠人一行行看？当 Agent 一天能产出几千行代码时，人根本看不过来。靠 Agent 自己审自己？它会"觉得"自己写得挺好——就像你自己检查自己的文章很难发现错别字一样。

自动门禁的作用是：**在代码进入正式版本之前，自动跑一系列检查。任何一项不通过，就不允许合并。** 不管代码是人写的还是 Agent 写的，走同一套关卡，没有例外。

## 核心原则

1. **写代码的和审查代码的必须分开**：用不同的 Agent（最好是不同的模型）来审查，避免"自己审自己"的盲区。
2. **门禁不全绿，别想合并**：这是硬规矩，不因为"赶时间"或"只是小改动"就放水。
3. **检查应该自动触发**：代码一提交就自动开始检查，不需要人手动启动。
4. **新项目自动继承**：所有项目走同一套门禁模板，新项目接入就自动拥有全套检查能力。

## 一套门禁通常包含什么

```
代码提交
  │
  ├── 格式检查：代码风格是否符合规范
  ├── 重复率检查：有没有大段复制粘贴
  ├── 自动化测试：现有的测试是否全部通过
  ├── 改动量检查：改动是否控制在合理范围内
  ├── AI 代码审查：独立 Agent 用不同视角审查代码
  ├── 规则式审查：用固定规则机械扫描（如 Open Code Review）
  └── 端到端测试：前端项目自动操作并录屏
       │
       ▼
  全部通过？ ──是──> 允许合并
       │
       否
       │
       ▼
  打回给 Agent 修复，修完重新提交
```

## AI 审查中的角色设计

门禁系统中的 AI 审查可以设置不同角色：

| 角色 | 影响门禁结果吗？ | 用途 |
|------|----------------|------|
| **主审** | 是 | 主审说不行就不能合并 |
| **顾问** | 否，但意见可见 | 提供参考意见，人自己判断要不要改 |
| **影子** | 否，且不可见 | 静默记录，用于事后评估审查质量 |

为什么要有"影子"角色？因为你想知道"主审是不是漏了什么"——影子审查不参与决策，但它的发现可以在事后和主审的结论对比，帮你校准审查的可靠性。

## 风险等级决定严格程度

不同项目需要不同程度的严格：

| 等级 | 场景 | 核心红线 |
|------|------|---------|
| **personal** | 自己用的工具 | 别丢数据、别静默出错、别崩溃 |
| **internal** | 小团队内部用 | 上一档 + 别越权访问 |
| **saas** | 对外提供服务 | 上一档 + 别被注入攻击、别泄露用户数据 |

个人项目不需要和对外服务一样严格——否则门禁带来的摩擦会大于它的价值。

## 怎么搭一套最小的门禁

**如果你只有一个项目、一个 Agent：**

1. 在 GitHub 上启用 GitHub Actions（免费）
2. 写一个 workflow 文件，让每次代码提交自动跑测试
3. 设置"测试不过不能合并"的分支保护规则

这就是最简版的门禁——三步搞定，零成本。

**如果你想加 AI 审查：**

4. 在 workflow 里加一步：用另一个 Agent（不同的模型）来审查代码变更
5. 把审查结果写成 PR 评论

**如果你有多个项目：**

6. 把 workflow 抽成一个可复用的模板，新项目只需要一行代码引用这个模板就能继承全套检查

## 根据你的情况调整

- **纯个人项目**：测试 + 改动量检查就够了，不需要多层 AI 审查。
- **前端项目**：一定要加端到端测试 + 录屏——前端的问题很多是视觉上的，测试通过不代表页面好看。
- **对外服务**：加安全扫描（如 [Codex Security](https://github.com/openai/codex-security)），定期跑，不用每次都跑。
- **成本敏感**：规则式审查（如 [Open Code Review](https://github.com/nicepkg/opencodereviewer)）远比 AI 审查便宜，效果覆盖面也很大——先用这个打底，重要项目再叠 AI 审查。
